## 概述

项目进度管理分为**技术进度**和**业务汇报**两个层面。技术进度由 AI Agent 自动维护（`docs/PROGRESS.md`），业务汇报面向管理层，需要将技术进度翻译为业务语言，通过飞书云文档呈现。

## 双轨进度管理

| 层面 | 文件/位置 | 受众 | 更新频率 | 维护者 |
|------|----------|------|---------|--------|
| 技术进度 | `docs/PROGRESS.md` | AI Agent、开发者 | 每次会话结束时 | Agent 自动 |
| 业务汇报 | 飞书云文档 | 管理层、跨团队 | 按需（周报/里程碑） | 开发者触发 Agent 协助 |

## 汇报触发时机

用户在 Cursor 中说以下关键词时触发汇报流程：

- "准备汇报" / "写周报" / "整理进度汇报"
- "更新飞书进度"

## 信息来源与整合

Agent 生成业务汇报时，按以下优先级采集信息：

1. **`docs/PROGRESS.md`**：技术进度（活跃工作、近期完成）
2. **`git log --since`**：近期提交记录（按模块聚合）
3. **各模块 `specs/INDEX.md`**：需求状态（Draft/Implemented）
4. **用户补充**：业务判断、百分比评估、后续规划（通过对话补充）

整合原则：
- 技术细节（如"删除 63 个模块级 Speckit 文件"）→ 转化为业务价值（如"开发效率提升"）
- 按功能模块分组，不按技术任务分组
- 进行中的工作标注完成度百分比
- 后续规划标注预期时间

## 汇报结构要求

### 章节结构（MUST 严格遵循）

| 章节 | 内容 | 要点 |
|------|------|------|
| **一、整体进度状态** | 全景快照：已完成/进行中/未启动 | 管理层 30 秒内掌握全貌 |
| **二、本期进展摘要** | 与上次汇报的增量对比 | 完成度变化表 + 关键交付清单 |
| **三、详细计划** | 按时间分段的具体任务 | 人+AI 协作周期，计划要紧凑 |

### 写作规则

1. **业务语言优先**：技术细节转化为业务价值（如"删除 63 个文件" → "开发效率提升"）
2. **按功能模块分组**：不按技术任务或 commit 分组
3. **进行中的工作标注完成度百分比**，并标注本期变化（如 50% → 65%）
4. **计划周期压缩**：人+Cursor 协作效率高，以天为粒度排本周、以周为粒度排后续
5. **增量对比必须有**：每次汇报 MUST 包含与上次汇报的完成度变化表

### 计划周期参考

| 时间粒度 | 适用范围 | 示例 |
|---------|---------|------|
| 本周（按天） | 当前冲刺的具体任务 | "4.10-4.13：卡顿归因准确率 ≥60%" |
| 下周 | 近期可预见的交付 | "4.14-4.18：全局 LLM 设置" |
| 月度 | 阶段性里程碑 | "4 月底：PerfDog Agent + 归因 ≥75%" |

## 飞书输出流程

Agent 使用飞书 MCP 的 `docx_builtin_import` 工具将 Markdown 汇报内容导入为飞书云文档：

```
触发：用户说"准备汇报"
  ↓
Agent 读取 PROGRESS.md + git log + specs/INDEX.md
  ↓
Agent 生成业务汇报 Markdown（与用户确认内容）
  ↓
调用 docx_builtin_import 导入飞书
  ↓
返回飞书文档链接给用户
```

飞书导入参数：
- `data.markdown`：汇报 Markdown 内容
- `data.file_name`：`"进度汇报-{YYYY-MM-DD}"`（最长 27 字符）
- `useUAT`：`true`（使用用户身份）
