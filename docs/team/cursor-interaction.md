## AI 协作核心原则

### 渐进式披露

按需加载上下文，避免预加载。先读索引/摘要确定相关性，再加载具体内容。

### Single Source of Truth

每条规则、知识只在一处维护。其他位置用引用指向权威源。优先级：constitution > rules > pitfalls > AGENTS.md。

### 确定性代码优先

重复性数值计算（时间戳转换、百分比、数据格式化）封装为辅助工具/脚本。LLM 负责推理和决策，数值计算交给确定性代码。

### 通用模板适配

AI 代码生成框架（如 Speckit）的通用模板往往包含广泛假设，MUST 根据项目实际技术栈和产品定位做裁剪适配。当产品本身是技术工具时，规格文档可合理包含技术约束。治理文档（constitution）的初始化与增量修订是不同操作。

### 规则精简

always-on 规则保持精简（每个 < 50 行），只包含不可违反的硬约束。详细知识通过 Skills 或知识文档按需加载，规则中只放指向文档的链接而非文档内容本身。

## 交互陷阱速查表

| 陷阱 | 说明 | 应对 |
|------|------|------|
| 实现偏离 | AI 理解了需求但实现方案偏离 spec | 使用 review-gate 规则，关键变更前输出决策摘要 |
| 规则遗忘 | 长对话后 AI 遗忘早期约束 | 在关键节点重新引用约束，或分拆为短会话 |
| 过度工程 | AI 倾向于过度设计而非最简方案 | 明确告知"最小可行方案"，限定文件和复杂度边界 |
| 文档过时 | 修改代码后忘记更新关联文档 | 实现完成后执行文档自检（review-gate 清单） |
| 文档归属误判 | AI 被关键词字面意思误导（如"架构"→ 放到 `doc/architecture/`），忽略内容实际影响范围 | 创建文档前先判断影响范围：仅影响单模块 → `modules/<name>/docs/`；跨模块 → `doc/` 对应子目录 |
| 已有规则未执行 | 规则已明确定义了操作路径，但 AI 仍提供选项让用户选择 | AI 应直接执行已有规则，只在规则未覆盖的场景才请求用户决策 |
| Bug 修复后未执行 review-gate | 完成 Bug 修复后，AI 未主动检查 review-gate 清单中的"是否有新的踩坑经验需要记录"，而是等用户提醒 | Bug 修复完成后 MUST 主动执行 review-gate 检查，评估根因是否非显而易见、是否建立了可复用原则，据此判定是否沉淀经验并向用户报告判定结果 |
| 信息冗余导致同步遗漏 | 同一知识（如路由表）在多处维护，新增内容时只更新了部分位置导致不一致 | 遵循 Single Source of Truth 原则：只保留一个权威源，其余位置用交叉引用。新增知识资产时 MUST 检查所有引用该类资产的索引/路由是否需要更新 |
| 规则重复导致不一致 | 同一条规则在 rules、constitution、pitfalls、AGENTS.md 多处出现，更新时遗漏某处导致矛盾 | 每条规则只有一个权威源，其他位置用引用指向 |
| 跨会话上下文丢失 | 新会话不知道之前的进度和决策 | 关键决策和进度记录到 spec/plan 文档中；多步骤任务主动标记当前进度 |
| 过度加载上下文 | 会话开始时预加载大量文件，导致后续交互质量下降 | 遵循渐进式披露：先读索引确定相关性，仅在确认需要时加载完整详情 |
| Skill 路由跳过导致工具误用 | 批量分析多个 trace 时，为了效率跳过场景路由，统一使用同一工具链分析所有 trace | MUST 先完成场景路由再选择工具。批量分析时逐个路由，不得统一使用同一工具链 |
| LLM 内联计算导致精度错误 | 让 LLM 手动进行时间戳格式转换（ns↔ms）、百分比计算等数值运算，容易出现量级错误 | 将重复性数据计算封装为辅助工具/脚本，LLM 负责推理和决策 |
| 批量分析工具返回膨胀导致上下文过载 | 一次性分析多个数据源，每个数据源的工具调用返回大量数据，累积后上下文爆炸，分析质量退化为数据罗列 | 批量分析 MUST 采用隔离策略：每个数据源独立 subagent 分析，仅返回结论摘要；主 agent 负责路由和汇总，不参与具体分析；优先使用 compact 模式减少返回量 |
