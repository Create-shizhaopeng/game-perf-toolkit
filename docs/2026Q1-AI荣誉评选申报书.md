### 1.1 项目简介

LV Game Toolkit 是一款面向 Android 游戏开发与测试场景的综合性工具集，集成设备管理、性能分析（Perfetto/PerfDog）、策略配置等核心能力，并通过 **AI Agent 驱动** 实现从"传统工具集"向"智能分析助手"的演进。

项目采用 **"Agent 驱动 + 模块化工具集 + 三端统一"** 架构：GUI（PyQt6）、CLI（Typer）、Agent（LLM 对话）三种交互方式共享同一套 Service API 业务逻辑层，不重复实现。

### 1.2 技术栈

| 类别 | 选型 |
|------|------|
| 语言 | Python 3.12+ |
| GUI 框架 | PyQt6 |
| CLI 框架 | Typer + Rich |
| 插件系统 | pluggy（pytest 同款） |
| 数据模型 | Pydantic 2.0+ |
| AI/LLM | pydantic-ai + LiteLLM（GLM-4 / Claude 多供应商切换） |
| 数据库 | SQLite + JSON 配置 |
| 打包 | PyInstaller onedir 模式 |
| 工程规范 | spec-kit 规范驱动开发 + Ruff 静态检查 |

## 2. 项目背景与痛点

### 2.1 业务背景

在 Android 游戏开发与调优场景中，开发者和 QA 工程师面临以下工作流程：

1. **设备准备**：配置 Android 设备，可能需要修改设备属性以适配不同机型测试
2. **性能采集**：使用 Perfetto/PerfDog 等工具采集帧率、卡顿、CPU/GPU 等性能数据
3. **Trace 分析**：对捕获的 Perfetto Trace 文件进行深度分析，定位卡顿/ANR/启动慢等问题
4. **策略配置**：根据分析结果调整游戏性能配置并推送到设备
5. **报告撰写**：汇总分析结果，编写优化建议报告

项目最初只是一个简单的小工具集合，架构设计未考虑多人通过 spec-kit + AI 协作开发大型项目的场景。随着工具数量增加，以下痛点逐渐凸显：

### 2.2 核心痛点

#### 痛点一：Perfetto Trace 分析门槛高

Perfetto Trace 文件分析需要专业工程师逐帧排查 SurfaceFlinger 延迟、BufferQueue 状态、Binder 调用链等 9 个维度（CPU、Thread、Binder、GPU、SF、IO、GC、Input、Lock）。一个完整的 Trace 分析流程包含：场景分类 → 帧检测 → 维度分析 → 归因排序 → 报告输出。

- **资深工程师**：约 30 分钟完成一次完整分析并出报告
- **新人工程师**：1 小时甚至更久，且容易遗漏关键细节点

#### 痛点二：性能分析经验高度依赖个人能力，新人培养周期长

性能分析是典型的"经验密集型"工作。不同工程师对同一份 Trace 文件的分析深度和结论差异很大，缺乏结构化的经验沉淀机制。项目中已沉淀的 34 项踩坑经验（如 Perfetto detach 须配合 write_into_file、SurfaceView 游戏帧数据采集需 SF fallback 等）此前散落在个人记忆中，无法被系统复用。

**新人培养周期**：
- **1～2 周**：熟悉 Trace 分析的操作，了解 Trace 可视化后的结构组成
- **3 个月**：初步掌握一些简单问题的分析，分析到比较浅层的原因
- **半年**：对于一些简单应用问题的 Trace 分析基本可以掌握
- **更久**：对于 Android 整体跨各个子系统、跨服务复杂场景的分析需要更长时间

#### 痛点三：工具碎片化、操作链路长

设备管理、性能采集、数据分析、策略配置分散在不同工具中。一个完整的调优流程需要在多个工具间切换，操作链路长。

#### 痛点四：分析报告编写重复劳动多

分析结果到最终报告的转化需要人工编写，每次分析后都要重复编写格式相似的报告，缺乏自动化报告生成能力。人工编写一份完整的性能分析报告需要 **20～30 分钟**。

### 2.3 解决目标

通过引入 AI Agent 技术，达成以下改善目标：

1. **降低分析门槛**：非资深工程师也能通过对话方式完成专业级的性能分析
2. **经验沉淀与复用**：建立分析经验的自动提取、存储和检索机制，实现"越用越聪明"
3. **工具链整合**：将分散的工具体系统一到一个平台，通过 AI Agent 统一编排
4. **自动化报告**：分析结果自动生成结构化报告，减少人工编写成本
5. **标准化流程**：通过 SOP（标准操作流程）机制确保分析质量的一致性

## 3. AI 解决方案

### 3.1 整体技术架构

项目 AI 能力分为三个层级，自底向上构建：

```
Layer 3: 全局 LLM 基础设施（LLMManager + Token 预算 + 状态机）
    ▲
Layer 2: Agent Chat 智能对话模块（对话循环 + 工具编排 + SOP 管理）
    ▲
Layer 1: Perfetto 智能分析 Agent（Main→Sub×N→Review 多 Agent 编排）
```

#### Layer 1：全局 LLM 基础设施

**LLMManager**（`toolkit/core/llm/manager.py`）是框架层 LLM 能力管理中心：

- **多 Provider 支持**：GLM-4（智谱 AI）和 Claude（Anthropic），通过 LiteLLM 统一抽象
- **状态机管理**：UNCONFIGURED → READY → DEGRADED → ERROR → BUDGET_PAUSED，状态变更通过 Qt 信号通知 UI
- **Token 预算管理**：上下文窗口动态追踪，支持预警阈值，超出预算自动暂停
- **配置持久化**：配置变更自动持久化，支持迁移历史配置
- **PyQt 信号集成**：config_changed、provider_changed、token_updated、budget_alert、error_occurred 等信号实时驱动 UI

#### Layer 2：Agent Chat 智能对话模块

基于 pydantic-ai + LiteLLM 构建的 AI Agent 对话系统，作为项目统一入口：

- **工具自动发现**：各功能模块通过 `register_agent_tools` 钩子声明能力，ToolRegistry 自动收集并生成 JSON Schema 用于 Function Calling，对缺少 parameters 的工具通过 `inspect.signature()` + `get_type_hints()` 自动补全
- **SOP 工作流管理**：内置 4 套标准操作流程（Trace 分析、PerfDog 分析、策略评审、Jank 综合分析），以 Markdown + YAML frontmatter 格式定义，支持自定义 SOP 导入/导出/删除
- **SOP 自动沉淀**：WorkflowTracker 记录工具调用序列，当检测到 2+ 工具无对应 SOP 时提示沉淀为新 SOP
- **MCP/Skills/Sub-agent 集成**：支持 Model Context Protocol 扩展工具能力，支持自定义 Skills 和子任务委派
- **知识索引**：ReportIndex 扫描历史报告目录提取摘要，注入 system prompt 增强上下文
- **对话持久化**：SQLite 存储全部对话历史，支持按日期分组检索
- **三端入口**：GUI Agent Tab（完整聊天界面）+ CLI（`agent ask` / `agent sop list`）

#### Layer 3：Perfetto 智能分析 Agent（核心 AI 能力）

项目最复杂的 AI 应用场景，实现了完整的多 Agent 推理链：

**多 Agent 编排架构**：
- **MainAgent**：意图分析 + 场景路由，将用户请求分类到 10 个分析场景之一
- **SubAgent × N**：深度 Trace 分析，支持 G0-G5 级别推理链增强
- **ReviewAgent**：交叉验证 + 独立审查，降低单一 Agent 误判

**10 大分析场景 SOP**：

| 场景 | SOP 文件 | 核心工具链 | 适用场景 |
|------|---------|-----------|---------|
| 卡顿/掉帧 | jank-analysis.md | pa_detect_jank → pa_analyze_dimension | 卡顿、丢帧、jank、fps |
| 响应时延 | response-latency.md | pa_execute_sql + 唤醒链追踪 | 响应慢、返回慢、点击延迟 |
| 输入时延 | input-latency.md | pa_execute_sql + buffer 分析 | 笔写时延、触控延迟、不跟手 |
| 启动性能 | startup-analysis.md | pa_execute_sql + pa_find_slices | 启动慢、冷启动、TTID |
| 转屏/配置变更 | rotation-analysis.md | pa_execute_sql + 唤醒链追踪 | 旋转慢、横竖屏切换 |
| ANR/无响应 | anr-analysis.md | pa_analyze_anr | ANR、卡死、freeze |
| 内存问题 | memory-analysis.md | pa_analyze_memory | 内存泄漏、OOM、heap |
| CPU/线程 | 维度分析 | pa_analyze_dimension(cpu/thread) | CPU 占用、线程阻塞 |
| IO 阻塞 | io-block-analysis.md | pa_analyze_dimension(io) | IO block、D-State |
| 通用/不明确 | general-analysis.md | 场景分类 → 路由 | "分析一下"、"看看性能" |

**G0-G5 推理链增强**：
- **Phase A（根因调查）**：优先维度先行（cpu → thread → binder），获取线程状态分布后按占比最高的异常状态选择下一步分析方向
- **Phase B（交叉验证）**：多维数据交叉验证，避免单一维度误判
- **Phase C（报告生成）**：按严重程度排序输出根因分析

**17 个 Agent 工具（pa_* 系列）**：
两套分析通道：引擎（本地 Python 分析器）+ MCP（Perfetto MCP Server，12 个工具），`pa_*` 工具自动路由，MCP 优先、失败降级引擎：

| 工具 | 数据源 | 用途 |
|------|--------|------|
| pa_trace_overview | 引擎 | Trace 元数据概览 |
| pa_detect_jank | 引擎 | 卡顿帧检测 |
| pa_analyze_dimension | MCP/引擎 | 单维度深度分析（9 个维度） |
| pa_thread_state_summary | MCP | 主线程状态分布 |
| pa_cpu_freq_analysis | MCP | CPU 核心与频率分析 |
| pa_find_slices | MCP | 搜索特定 slice |
| pa_execute_sql | MCP | 自定义 SQL 查询 |
| pa_analyze_anr | MCP | ANR 检测与根因分析 |
| pa_analyze_memory | MCP | 内存泄漏与堆分析 |
| pa_compress_results | 本地 | 结果压缩摘要 |
| pa_analyze | 引擎 | 完整分析流水线 + 报告 |
| pa_parse | 引擎 | Phase 1 丢帧解析 |
| pa_analyze_dims | 引擎 | 指定维度分析 |
| pa_list_dims | 引擎 | 列出可用维度 |
| pa_history | 数据库 | 查询分析历史记录 |

**Prompt 预算管理**：
- ToolReturn 结构化压缩：≤300 token 摘要 + metadata 保留原始数据，severity-aware retention
- 动态上下文窗口追踪，防止 "Prompt exceeds max length" 错误
- 冗余工具移除：11→9 个，减少无效 Token 消耗

**经验学习系统**：
- 分析结果自动提取为 Learnings，存储为结构化案例
- 基于相似度检索历史案例注入当前分析上下文
- 包含实际案例库：LOLM 假阳性误判案例、Face Unlock 音频卡顿案例等

**场景感知预取**：
根据 SOP frontmatter 中定义的 prefetch 规则，在分析启动阶段预取相关工具数据（如 jank 场景预取 detect_jank 和 trace_overview），减少冗余调用。

**5 种渲染管线自动识别**：
标准 HWUI、游戏 EGL、游戏 Vulkan、Flutter、WebView，自动识别帧边界标记，适配不同类型游戏。

### 3.2 积累的核心 Skill

项目从实践中沉淀出以下 AI Skill：

#### Skill 1：perfetto-analysis（Perfetto Trace 全场景性能分析）

- **描述**：涵盖卡顿/ANR/内存/启动/CPU/IO/输入延迟/转屏等多场景的 Perfetto Trace 分析 Skill
- **架构**：MCP + 引擎混合架构，提供 17 个原子工具集，按场景路由分析策略
- **资源组成**：9 套 SOP 文档、根因模式库、案例库、SQL 查询模式、设备调优参考、完整工具目录
- **触发条件**：当用户提到 Perfetto、trace 分析、卡顿、丢帧、jank、fps、帧率、ANR、内存泄漏、启动慢、CPU 占用、线程阻塞时自动触发
- **分析流程**：确认分析目标 → Trace 概览 + 场景分类 → 按 SOP 执行分析 → 归因排序 → 输出结论

#### Skill 2：knowledge-curator（知识策展）

- **描述**：对分析经验和知识资产进行策展管理的 Skill
- **用途**：支持知识资产的分类、索引和复用

### 3.4 创新亮点

1. **三端统一架构**：GUI/CLI/Agent 共享同一套 Service API，业务逻辑不重复实现，从"传统工具集"平滑演进为"AI 驱动的智能平台"

2. **Spec-Driven + AI 协作开发模式**：采用 spec-kit 规范驱动开发（specify → clarify → plan → tasks → implement），结合 AI Agent 实现多人并行开发，7 个模块 + 16 个 Spec 同时推进

3. **多 Agent 推理链编排**：在 Perfetto 分析场景中实现 Main→Sub×N→Review 三层次编排，配合 Phase 感知预取和经验学习，构建完整的推理闭环

4. **MCP + 引擎混合架构**：Perfetto 分析创新性地采用 MCP Server + 本地引擎双通道方案，17 个工具自动路由，MCP 优先、失败降级，兼顾灵活性和可靠性

5. **Prompt 预算管理**：首创 ToolReturn 结构化压缩机制（≤300 token + severity-aware retention），彻底解决 "Prompt 超出 max length" 问题

6. **经验自动沉淀**：SOP 以 Markdown + YAML frontmatter 格式定义，支持 10 大场景路由 + 预取规则；Learnings 系统自动提取历史案例，形成"使用 → 积累 → 复用 → 优化"的正向循环

7. **Monorepo 下的 Speckit 分层管理**：实现主 Speckit + 模块独立 Speckit（--no-git）+ 规则继承机制（Cursor Rules → AGENTS.md → SDK 强制），支持多人 AI 协作开发

### 3.5 关键 Prompt 示例

项目中 Perfetto 分析 Agent 使用结构化 Prompt 模板（`modules/perfetto_analysis/src/agent/prompts.py`），包含系统提示词、场景元数据、SOP 正文三部分：

- **系统提示词**：角色定义 + 分析场景 + SOP 步骤 + 工具列表
- **推理链 Prompt**：Phase A/B/C 分阶段引导
- **工具描述**：自动从 Pydantic 模型生成 JSON Schema

SOP 文件采用 Markdown + YAML frontmatter 格式，以卡顿分析 SOP 为例：

```yaml
---
scene: jank
display_name: 卡顿分析
priority_dims: [cpu, thread, binder]
secondary_dims: [gpu, sf, io]
optional_dims: [gc, input, lock]
prefetch:
  - tool: detect_jank
    inject_as: jank_frames
  - tool: trace_overview
    inject_as: trace_info
---
```

分析流程遵循 6 步结构：确认分析目标 → Trace 概览 + 场景分类 → 渲染管线识别 → 维度分析 → 线程状态分布后的分支决策 → 归因与输出。

对话循环的 System Prompt 动态组装 SOP 元数据 + 工具列表 + 历史报告摘要（`modules/agent_chat/src/service.py`）。

```
日均分析频次 = (游戏分析次数 + 超分插帧分析次数) ÷ 统计天数

游戏分析次数 = Σ(每个游戏迭代轮次 × 3 模式)
  假设 30 个游戏中 20 个简单（4 轮）、10 个复杂（10 轮）
  = (20×4 + 10×10) × 3 = 540 次/2个月 ≈ 9 次/天

超分插帧分析次数 = 30+ 需求 / 1个月 ≈ 1.5 次/天

日均合计 ≈ 10～12 次
```

## 6. 风险控制

### 6.1 AI 幻觉处理

本项目在确保 AI 输出准确性方面采取了多层次措施：

1. **结构化输出约束**：所有 Agent 工具的输入/输出均通过 Pydantic 模型验证，确保数据格式正确，杜绝自由文本导致的格式错误

2. **多 Agent 交叉验证**：ReviewAgent 对 SubAgent 的分析结果进行独立审查，降低单一 Agent 的误判风险

3. **经验学习机制**：Learnings 系统检索历史相似案例（如 LOLM 假阳性误判案例、Face Unlock 音频卡顿案例），用实际经验校准当前分析结论

4. **SOP 标准化流程**：10 套预定义 SOP 引导 Agent 按步骤分析（确认目标 → 场景分类 → 渲染管线识别 → 维度分析 → 分支决策 → 归因输出），避免跳跃性推理

5. **ToolReturn 压缩机制**：工具返回结构化摘要（≤300 token + severity-aware retention），保留关键信息的同时控制幻觉空间

6. **引擎 + MCP 双通道**：分析工具支持引擎和 MCP 两种数据源，自动路由 + 失败降级，避免因单一数据源异常导致错误结论

7. **渲染管线自动识别**：5 种渲染管线（HWUI/EGL/Vulkan/Flutter/WebView）自动识别，不同管线使用不同帧检测策略，避免误判

8. **已知误判模式库**：维护 patterns/root-cause-patterns.md，记录已知误判场景，引导 Agent 避开陷阱

### 6.2 数据安全

| 项目 | 说明 |
|------|------|
| Trace 文件处理 | Perfetto Trace 文件的分析在本地引擎端执行（Python 分析器），SQL 查询通过 MCP Server 本地执行 |
| 上传 LLM 的数据 | 仅包含 Trace 中的一些被大众所知晓的内容，不包含客户敏感信息。发送给 LLM 的是分析结果的结构化摘要和工具返回摘要，原始 Trace 文件不上传 |
| API Key 管理 | 由用户自行添加，框架层不存储 API Key |
| 数据脱敏 | 上传内容仅含公开性能数据，不含客户敏感信息 |

### 6.3 合规审查

| 项目 | 说明 |
|------|------|
| 数据出境 | 不涉及。上传 LLM 内容仅包含 Trace 中被大众所知晓的内容，不包含客户敏感信息 |
| 主要依赖协议 | PyQt6 (GPL/商业)、pluggy (MIT)、typer (MIT)、pydantic (MIT)、pydantic-ai (MIT)、litellm (MIT)、Rich (MIT) |

### 6.4 人工复核

当前在规划迭代中，涉及 Trace 分析的部分将增加**分析结论回归指向源文件的可视化**功能，使用户能够对照原始 Trace 数据验证 AI 分析结论，实现人工复核能力。
