
# 文档驱动记忆系统：一键搭建 Prompt

> **使用方法**：将下方整段内容复制粘贴发送给 Cursor，它会自动为你的项目创建文档目录、初始化核心文件、配置两条协同 Rule。

---

帮我在当前项目中搭建一套文档驱动的记忆系统。请完成以下全部操作：

## 一、创建目录结构

```
docs/
├── PROGRESS.md          # 项目进度总览（核心入口，AI 每次必读）
├── analyze/             # 技术分析文档（ANAL-XXX）
│   └── SUMMARY.md       # 该目录的文档索引/记忆压缩
├── design/              # 设计方案文档（DES-XXX）
│   └── SUMMARY.md
├── bugfix/              # Bug 分析文档（BUG-XXX）
│   └── SUMMARY.md
├── journal/             # 每日工作记录（YYYY-MM-DD.md）
│   └── SUMMARY.md
└── archive/             # 归档（已完结的文档）
```

每个子目录下都有一个 SUMMARY.md，作为该目录所有文档的索引和摘要，用于记忆压缩。

## 二、初始化 PROGRESS.md

请根据当前代码库的实际情况，填写以下内容：

- 项目名称 + 一句话描述
- 当前阶段概述（根据代码库判断）
- 技术栈列表（从 package.json / pom.xml / requirements.txt 等推断）
- 活跃文档列表（留空表格：编号 | 类型 | 标题 | 状态 | 最后更新）
- 近期工作（留空，后续按以下三层结构自动填充）
- 文档统计（留空表格：类型 | 数量）

近期工作采用**三层任务描述法**，从粗到细逐层展开：

```markdown
## 近期工作（最新在上）

### 2026-04-07（预处理任务停止/取消功能）       ← L1：可交付任务
                                                  能独立写进日报，对应一个明确结果输出

- **Python 服务**：                               ← L2：子任务（标准工作单元）
  - 新增 `POST /cancel` endpoint                   每个 L2 是一个可独立验证的最小交付
  - Worker 支持 `cancel_event` 中断循环
  - 修复 Session 状态为 3（已取消）时的持久化逻辑
- **Java 后端**：
  - `PreprocessSessionController` 新增 cancel 转发 API
  - 修复 `selectBaymaxTestPreprocessSessionList` 缺少 case_set_id 过滤
  - `cancelByCaseSetId()` 改为取最新活跃 Session（max ID）
- **Vue 前端**：
  - 用例集列表新增"停止预处理"按钮（状态联动：仅 processing 时可见）
  - 禁用 request.ts 的重复提交拦截器（cancel API 需要快速连续发送）
- **产出文档**：BUG-014（cancel 命中错误 Session 根因分析）
```

三层结构的设计意图：

| 层级 | 名称 | 粒度 | 用途 | PROGRESS.md 中的位置 |
|------|------|------|------|---------------------|
| **L0** | 主题层 | 前端迁移 / 预处理优化 / 网关设计 | 阶段性汇总，看大盘 | 顶部的"工作主线"表格 |
| **L1** | 可交付任务 | `### YYYY-MM-DD（标题）` | 日报/周报粒度，做时间归因 | 近期工作的每个标题行 |
| **L2** | 子任务 | 标题下的末端 bullet | 最小可交付单元，做效率度量 | 近期工作标题下的具体条目 |

这种分层结构有两个好处：
1. **AI 快速定位**：读 L1 标题即可了解"最近在做什么"，需要细节时再展开 L2
2. **可度量**：L2 是标准工作单元，可用于衡量"完成一个任务花了多少 Token / 多少时间"

## 三、初始化各子目录的 SUMMARY.md

在 analyze/、design/、bugfix/、journal/ 下各创建一个 SUMMARY.md，作为该目录的文档索引。格式：每个文档一行 `| 编号 | 标题 | 状态 | 核心结论（一句话）|`

## 四、创建 Rule 1：docs-driven-workflow.mdc（始终触发）

文件路径：`.cursor/rules/docs-driven-workflow.mdc`

```
---
description: 文档驱动工作流。在执行任何代码修改、分析、调试之前，先阅读相关文档建立上下文；在完成修改之后，同步更新受影响的文档。始终自动触发。
alwaysApply: true
---

# 文档驱动工作流：改代码前先读文档，改完代码后更新文档

## 原则

所有工作必须有文档支撑。代码变更不是终点——文档同步更新才是。

## 操作前：建立上下文

在回答用户问题或执行任何修改之前，**必须先阅读相关文档**：

### 1. 每次对话开始时

- 读取 `docs/PROGRESS.md` 了解项目当前阶段和活跃任务
- 读取 `docs/analyze/SUMMARY.md`（如存在）获取文档索引

### 2. 修改代码前

- 在 `docs/analyze/SUMMARY.md` 中检索与当前修改相关的文档
- 搜索 `docs/` 下是否有与目标模块相关的 analyze/design/bugfix 文档
- 阅读找到的相关文档，了解已知问题、历史改动和设计决策

### 3. 分析问题前

- 搜索 `docs/analyze/` 和 `docs/bugfix/` 下是否已有相关分析
- 避免重复分析已有结论的问题

## 操作后：同步文档

完成代码修改或分析后，**必须更新以下文档**：

### 1. 始终更新

- `docs/PROGRESS.md`：在"近期工作"中追加本次变更摘要

### 2. 按需更新

| 变更类型 | 需要更新的文档 |
|---------|-------------|
| 修改某模块代码/配置 | 该模块对应的分析文档（如有问题清单则标记已修复） |
| 修复 Bug | 创建或更新 `bugfix/BUG-XXX` 文档 |
| 新增分析发现 | 更新对应的问题清单或创建新 ANAL 文档 |
| 创建新文档 | PROGRESS.md 的"活跃文档"列表、SUMMARY.md 的索引 |

### 3. 新建文档时

- 按编号规则分配编号（ANAL-XXX / DES-XXX / BUG-XXX，自动扫描目录获取下一个编号）
- 文件名使用 kebab-case：`ANAL-XXX-short-description.md`
- 在 PROGRESS.md 中登记
- 在 SUMMARY.md 中添加索引条目

## 文档状态卡片

每个文档顶部必须包含状态卡片（HTML 注释）：

<!--
  📋 状态卡片
  id: ANAL-001
  title: 文档标题
  type: analyze | design | bugfix
  status: draft | active | done | superseded
  created: YYYY-MM-DD
  updated: YYYY-MM-DD
  tags: [标签1, 标签2]
-->

状态流转：
- analyze: draft → active → done | superseded
- design: draft → active → implemented | deprecated
- bugfix: investigating → root-caused → fixed | wontfix

superseded/deprecated 时必须标注 `superseded_by: XXX-XXX`。

## 文档间引用

- 行内引用：`详见 ANAL-019（问题清单）`
- 依赖声明：状态卡片中添加 `depends_on: [ANAL-010, DES-001]`
- 上游文档更新时，检查下游依赖文档是否需要同步更新

## 禁止事项

- 禁止不读相关文档就直接修改代码
- 禁止完成代码修改后不更新任何文档
- 禁止创建新文档但不在 PROGRESS.md 中登记
- 禁止分析已有明确结论的问题而不引用已有文档
```

## 五、创建 Rule 2：docs-workflow.mdc（按需触发）

文件路径：`.cursor/rules/docs-workflow.mdc`

```
---
description: 工作文档库管理规则。当用户提到"写日志"、"写设计方案"、"写bug分析"、"看进度"、"项目进度"、"新建文档"、"更新进度"、"工作记录"、"归档"时触发。
globs:
  - docs/**
alwaysApply: false
---

# 工作文档库管理规则

## 当用户说"看进度"或"项目进度"

1. 读取 `docs/PROGRESS.md`
2. 汇报当前阶段、活跃文档、近期工作、待办事项
3. 基于待办和文档状态提出建议

## 当用户说"写日志"或"工作记录"

1. 询问日期（默认今天）
2. 创建 `docs/journal/YYYY-MM-DD.md`
3. 如果用户描述了做的事，自动填充"完成内容"
4. 更新 `docs/PROGRESS.md` 的"近期工作"

## 当用户说"写设计方案"

1. 扫描 `docs/design/` 目录获取下一个编号
2. 询问方案标题和相关模块
3. 创建文档（含状态卡片），在 PROGRESS.md 中登记

## 当用户说"写 bug 分析"

1. 扫描 `docs/bugfix/` 目录获取下一个编号
2. 基于用户描述创建文档（含现象/根因/修复方案结构）
3. 在 PROGRESS.md 中登记

## 当用户说"更新进度"

1. 扫描所有目录下文档的状态卡片
2. 重新生成 PROGRESS.md 的活跃文档列表和文档统计
3. 如果用户描述了新工作内容，追加到"近期工作"

## 当用户说"归档"

1. 确认归档范围
2. 移动到 `docs/archive/` 对应子目录
3. 更新 PROGRESS.md 和 SUMMARY.md
4. 归档文档保留原始编号，新编号继续递增

## 重要提醒

- 文档编号不可重复，始终递增
- 日期格式统一 YYYY-MM-DD
- deprecated/superseded 的文档不要基于它给建议
```

---

## 搭建完成后的使用说明

执行以上 Prompt 后，你将拥有一套完整的记忆系统。两条 Rule 分工明确：

- **Rule 1**（`alwaysApply: true`）：每次对话自动触发，驱动"先读后写"的记忆循环
- **Rule 2**（按需触发）：当你说"看进度"、"写日志"、"写设计方案"等指令时激活，处理文档管理操作

之后正常与 Cursor 对话即可。Rule 1 确保 AI 每次都先读 PROGRESS.md 了解上下文，完成工作后自动回写文档。Rule 2 让你可以用自然语言管理文档库。随着项目推进，文档自然积累，形成越来越完整的项目记忆。

文档积累到 10+ 篇时，告诉 Cursor"更新 SUMMARY.md"做一次索引压缩即可。
