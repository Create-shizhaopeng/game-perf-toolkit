# Feature Specification: gameperfconfig 多文件对比与合并

**Feature Branch**: `007-gameperf-config-diff`  
**Created**: 2026-04-03  
**Status**: Specified（需求已细化，可进入 tasks / implement）  
**Input**: 用户描述：选择两个或多个 gameperfconfig 类 XML 文件进行对比；展示差异项；支持在版本间互相采纳替换；保存前需用户确认；支持从已连接设备读取设备上的配置文件参与对比；确认保存后落盘生效。

**产品归属**: 本能力作为 **`workspace_tools`（侧边栏展示名：**性能配置对比**）** 模块内的用户功能交付；与 **性能配置（game_perf）** 在 **设备路径、文件名约定、XML 语义** 上对齐，但 **不依赖** `game_perf` 源码导入（遵守模块隔离）。规格正文保持实现无关。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 选择基准与多个对比文件 (Priority: P1)

作为游戏性能测试工程师，我需要指定 **一个基准配置文件**，并追加 **一个或多个** 其他 `gameperfconfig`（或项目约定的有效命名）XML 文件，以便在同一界面中发起对比。

**Why this priority**: 没有明确的多文件输入，后续差异展示与合并无从谈起。

**Independent Test**: 仅实现文件选择与列表管理（尚未合并）时，仍可验收「可选基准 + 多文件、可移除、可替换基准」流程。

**Acceptance Scenarios**:

1. **Given** 用户已通过浏览或拖拽选择本地 XML，**When** 文件名校验符合项目对 gameperfconfig 的约定且解析为合法 XML，**Then** 文件进入对比列表并显示标识（基准 / 对比）
2. **Given** 已选定基准与至少一个对比文件，**When** 用户点击「开始对比」（或等价操作），**Then** 系统生成对比结果视图（见 US2），非法或无法解析的文件得到明确错误说明且不阻塞其他合法文件处理（若产品选择「全量成功才对比」须在 Assumptions 中写明；**默认**：跳过坏文件并提示）
3. **Given** 用户仅选择了一个文件，**When** 尝试对比，**Then** 提示至少需要一个对比对象（或引导再选一份）

---

### User Story 2 - 展示差异并双向采纳替换 (Priority: P1)

作为游戏性能测试工程师，我需要 **看到结构化差异**（例如按游戏、模式、策略节点、频率项等可理解的层级），并能对单项或成组差异选择 **采用基准侧内容** 或 **采用某一对比文件侧内容**，在内存中形成待保存的合并结果。

**Why this priority**: 核心价值是「看懂差在哪里」并「有控制地合并」。

**Independent Test**: 使用两份已知差异的样例 XML，在不接设备的情况下完成差异列表展示与一次采纳操作，合并结果在内存预览中与预期一致。

**Acceptance Scenarios**:

1. **Given** 已完成多文件对比，**When** 用户展开某差异项，**Then** 能同时看到各侧取值（或等效展示），并明确当前基准与对比来源文件名/标签
2. **Given** 某差异项支持采纳，**When** 用户选择「采用 A 侧」或「采用 B 侧」（或多文件时指定来源侧），**Then** 合并预览更新，且可撤销该次采纳（至少支持一步撤销或重置为对比前状态）
3. **Given** 用户未做任何采纳，**When** 查看合并预览，**Then** 与基准文件内容一致（或产品定义的初始策略一致，须在 Assumptions 中固定）

---

### User Story 3 - 保存前确认与落盘生效 (Priority: P1)

作为游戏性能测试工程师，我在完成采纳后点击保存时，系统 **必须** 弹出确认对话框（摘要：目标路径、是否覆盖、影响范围要点），我确认后 **才** 将合并结果写入用户选择的保存路径并 **立即在磁盘生效**。

**Why this priority**: 误覆盖生产或设备相关配置风险高，确认与落盘是安全闭环。

**Independent Test**: 采纳一项差异后保存到临时副本路径，确认对话框文案完整；取消保存时文件未被修改。

**Acceptance Scenarios**:

1. **Given** 合并结果与磁盘上目标文件不一致，**When** 用户触发保存，**Then** 出现确认对话框，取消则无任何写盘
2. **Given** 用户在确认对话框中选择确定，**When** 写盘成功，**Then** 提示成功且后续重新打开该路径文件内容与合并结果一致
3. **Given** 写盘失败（权限、只读、磁盘满等），**When** 保存结束，**Then** 用户得到可读错误说明，且原有文件不被截断损坏（原子替换或先写临时再替换为产品约定策略）

---

### User Story 4 - 从设备读取配置文件参与对比 (Priority: P2)

作为游戏性能测试工程师，我可以在设备已连接且工具已选 Serial 的前提下，将 **设备上的 gameperfconfig**（与现有「性能配置」模块推送目标路径一致的标准路径）作为 **对比来源之一** 拉取到本地临时副本并参与对比，而无需事先手动 adb pull。

**Why this priority**: 与「本地多文件对比」相比，设备拉取是增强闭环，可独立迭代。

**Independent Test**: Mock 或真机拉取成功后，对比列表中出现「设备」来源标识，且与本地文件对比结果正确；拉取失败时错误可理解且不影响已选本地文件。

**Acceptance Scenarios**:

1. **Given** 设备已连接且权限足够，**When** 用户选择「从当前设备添加」，**Then** 拉取标准路径配置并作为对比文件之一加入列表（只读缓存语义，保存默认不写回设备除非用户另有显式操作——**默认** 保存仅写用户选择的本机路径；写回设备属 Out of Scope 除非未来单独规格）
2. **Given** 设备未连接或拉取失败，**When** 用户尝试添加设备侧文件，**Then** 明确提示原因，不崩溃
3. **Given** 设备文件与本地基准对比完成，**When** 用户采纳合并并保存到本机路径，**Then** 行为与 US3 一致（本规格不强制推送设备）

---

### Edge Cases

- 多份对比文件与基准 **完全相同**：应提示无差异或可空状态，保存可选禁用或仅允许「另存副本」
- XML 合法但 **语义异常**（缺 GamePolicy、空游戏列表等）：差异引擎应降级为可理解的区块或行级说明，而非静默空白
- **编码非 UTF-8**：按与现有 game_perf 解析一致的容错策略（如替换非法字节），并在界面标明可能影响准确度
- **超大文件**（数 MB 级）：对比与界面仍应完成或可配置上限并提示（具体上限实现阶段定，规格要求 **有界行为**——不无限卡死）
- 用户在对比过程中 **更换基准**：应清空或重新计算差异，并提示未保存的合并将丢失（或提供确认）
- **并发修改**：若磁盘上文件在外部被修改，保存前可提示「文件已变更」并让用户选择重新加载或覆盖（实现阶段定策略，规格要求 **不得静默覆盖**）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户指定 **恰好一个基准文件** 与 **至少一个对比文件**（对比文件可来自本机或设备拉取缓存）
- **FR-002**: 系统 MUST 仅接受符合项目约定的 gameperfconfig 类 XML（文件名与格式校验与现有「性能配置」模块策略对齐）
- **FR-003**: 系统 MUST 以 **用户可理解的结构化方式** 列出差异（不少于：游戏/包维度、模式维度、以及关键策略与频率相关节点的差异归类；具体树形与字段实现阶段细化）
- **FR-004**: 用户 MUST 能对可合并的差异项执行 **双向采纳**（从基准或从指定对比来源采纳到合并结果），并能在保存前 **撤销** 最近一次采纳或整体重置合并状态（至少一种可测的撤销路径）
- **FR-005**: 用户触发保存时，系统 MUST 展示 **确认对话框**（含目标路径、是否覆盖已有文件、简要变更提示），用户取消则 MUST NOT 写盘
- **FR-006**: 用户确认保存后，系统 MUST 将合并结果写入用户选定路径并 **持久化成功后可被再次打开验证**
- **FR-007**: 在设备可用时，系统 MUST 支持将 **设备标准路径上的 gameperfconfig** 作为对比输入之一（路径与现有 game_perf 推送目标一致）
- **FR-008**: 任一步失败（解析、拉取、保存）时，系统 MUST 给出 **可读错误信息**，且保持应用处于稳定状态（无未处理崩溃）

### 补充功能需求（实现级）

以下在 FR-001～FR-008 基础上细化，便于任务拆分与验收（仍保持「做什么」而非具体类名）。

- **FR-009（入口与可见性）**: **性能配置对比** Tab 内 MUST 提供明确入口（子区域、子 Tab 或分组标题），用户 **无需** 进入「游戏性能配置」Tab 即可完成对比全流程。
- **FR-010（文件名与根节点）**: 本地文件 MUST 满足与性能配置模块 **相同** 的约定：文件名包含子串 **`gameperfconfig`** 且扩展名为 **`.xml`**；根元素 MUST 为 **`GameOptPolicy`**（含 `version` 属性时可参与差异或单独列出）。
- **FR-011（设备路径）**: 从设备读取时，远程路径 MUST 为 **`/system/etc/gameperfconfig.xml`**；本地缓存路径语义与性能配置拉取一致：**`<data_dir>/pull_cache/<serial>/gameperfconfig.xml`**（`data_dir` 与主应用一致）。
- **FR-012（差异最小粒度 — MVP）**: 结构化差异 MUST 至少覆盖：**PreEnv**（cluster 文本差异）、**BaseInfo/Game/SceneList**、**GamePolicy 下各 Game → Mode → ThermalSceneCode/PerfHint/Policy/TempLevel/item/BindCore/tid** 等可定位节点；**仅顺序变化**可合并为单条「子节点顺序变化」或降级展示（实现可选，须在 UI 标明）。
- **FR-013（对比交互）**: MUST 支持 **切换当前对比文件**（相对基准）查看差异树；多对比文件时 **摘要区** 显示每个对比文件相对基准的 **差异条数**（或「无差异」）。
- **FR-014（长操作）**: **开始对比** 与 **从设备拉取** MUST 不阻塞 UI；用户 MUST 能 **取消** 进行中的拉取/对比（与性能配置模块「取消自动拉取」语义一致：单次 ADB 步骤内可能无法中断，但步骤之间可检查取消）。
- **FR-015（保存确认内容）**: 确认对话框 MUST 至少展示：**目标完整路径**、**是否覆盖已存在文件**、**当前是否存在未采纳合并（脏状态）** 的提示；若目标文件在会话开始后曾被外部修改，MUST 提示 **重新加载 / 仍覆盖**（二选一或等价）。

### 非功能需求

- **NFR-001**: `workspace_tools` 实现 MUST **禁止** `import modules.game_perf.src.*`；与 game_perf 仅 **字符串常量与行为约定** 对齐。
- **NFR-002**: Service 层 MUST 保持 **纯同步**、无 PyQt；线程内工作由 GUI 以 **QThread** 调用。
- **NFR-003**: `context` 键 MUST 使用 **`wo_` 前缀**（如 `wo_gameperf_diff_service`）。
- **NFR-004**: 写盘 MUST 优先 **临时文件 + 原子替换**（`os.replace` 或平台等价），失败时原文件完整可读。

### Key Entities

- **对比会话（Comparison Session）**: 一次用户操作上下文，包含基准文件引用、对比文件集合、合并工作副本状态、未保存标记
- **差异项（Diff Item）**: 可定位到配置语义路径的一条或多条差异（含各侧取值、严重级别如「结构缺失」与「值不同」）
- **文件来源（File Provenance）**: 本地路径、设备 Serial + 标准路径、临时缓存路径等，用于界面标注与日志

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在标准样例（两份故意制造 5 处以上可识别差异的 XML）下，用户 **无需外部文档** 即可在 **3 分钟内** 找到全部差异入口并完成至少 **2 处** 采纳操作
- **SC-002**: **100%** 的保存操作在写盘前经过显式确认；抽样测试中 **0** 次「误触即覆盖」无对话框写盘
- **SC-003**: 设备拉取成功时，**90%** 以上用户能在首次尝试中理解「设备来源」与「本地文件」在列表中的区别（可用可用性测试或内部走查表验证）
- **SC-004**: 对 **10MB 以内** 的典型配置文件，对比结果在 **可接受等待时间** 内呈现（具体秒级指标在计划中结合硬件定义；规格要求可测且需写入 plan 验收）

## Assumptions

- **多文件模型**：采用 **单基准 + 多对比**；任一时刻合并目标是单一工作副本（从基准派生），用户从各对比文件挑选采纳。若未来需要「无基准、全 pairwise」可另开规格扩展。
- **保存范围**：默认 **仅保存到用户选择的本机路径**；**不包含** 自动 push 到设备（与现有推送流程解耦，避免本规格范围膨胀）。
- **与现有模块关系**：文件名规则、设备路径、编码容错与 **game_perf 产品行为对齐**；**实现上** 在 `workspace_tools` 内 **自行实现或复制常量**（不 import game_perf `src`）；**ADB** 使用应用注入的 **`context["adb"]`**（`AdbManager`）。不在本规格中要求修改 `toolkit` 公共 API。
- **合法 XML**：对比前对各文件做与 game_perf 一致的合法性检查；不合法文件不进入合并链。

## Out of Scope

- 自动推送合并结果到设备（可引用现有「性能配置」Tab 的推送流程由用户手动完成）
- 非 gameperfconfig 的通用 XML diff 工具
- 版本控制（Git）集成与三路合并（BASE/MINE/THEIRS）

## Clarifications

### Session 2026-04-03（需求细化）

- **Q1**: 坏文件策略？ → **A**: 默认 **跳过** 无法解析的文件并 **列表内红字/日志** 提示；不阻止其余文件参与对比（与 US1 一致）。
- **Q2**: 合并预览形态？ → **A**: MVP 以 **差异树 + 采纳状态图标/标签** 为主；可选 **只读 XML 预览** 为 P3（tasks 可标可选）。
- **Q3**: 撤销深度？ → **A**: MVP **至少**「撤销上一次采纳」+「重置为基准」；完整多步撤销栈为增强项。
- **Q4**: 与性能配置同时打开同一文件？ → **A**: 不强制文件锁；保存前 **FR-015** 外部修改检测为 **尽力而为**（mtime 或大小变化提示）。
